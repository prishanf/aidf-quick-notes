# Adapter guide

An adapter is a thin translation from an AI tool's instruction mechanism to AIDF. The framework documents stay canonical; the adapter points at them.

**AIDF ships no vendor command files.** The three adapter files in this repository (`.claude/`, `.codex/`, `.cursor/`) are instruction pointers only. This is deliberate: v1 shipped an adapter that advertised `/spec`, `/plan`, `/build`, `/review`, and `/ship` while providing no command directory, so none of those commands existed. An adapter that promises a surface it does not deliver is worse than no adapter, because the failure is silent — the agent simply does something else.

`reference/scripts/check-consistency.sh` now fails the build if an adapter file advertises a command surface the repository does not ship.

## Wiring the contracts on your surface

**`reference/scripts/aidf-install.sh` already does this for Claude Code, Codex, and Cursor** when it installs into a project — one file per contract in `.claude/commands/`, plus the two instruction pointers. That is the distinction that matters: the *framework repository* ships no vendor command surface, while an *installed project* gets a working one. Read on only if your surface is not one of those three, or you want to change what was generated.

Each of these takes minutes. Do it in *your* project, where you control the surface.

| Surface | Mechanism | How |
|---|---|---|
| Claude Code | `.claude/commands/<name>.md` | One file per contract; each can be a single line: `Follow the contract in .aidf/commands/spec.md.` The filename becomes the slash command. Generated by the installer. |
| Codex | `AGENTS.md` + task prompt | Reference the contract file by path in the task prompt. Generated by the installer. |
| Cursor | `.cursor/rules/*.mdc` | An always-on rule pointing at `AGENTS.md`; add per-role rules with `globs` if you want them scoped. Generated by the installer. |
| Gemini CLI | Project instruction file | Load `AGENTS.md` and the active contract. |
| Aider | `--read` context files | Include `AGENTS.md`, the manifest, and the active artifact. |
| OpenHands | Repository instructions / microagents | Same role, scope, and evidence contract. |
| Anything else | Its native repository-instruction surface | Translate; do not redefine. |

## Adapter requirements

An adapter must:

1. point to `AGENTS.md`;
2. identify the project manifest;
3. make the eight command contracts reachable — by whatever mechanism the surface offers;
4. preserve human approval and release gates;
5. promise nothing the repository does not ship;
6. stay short enough to audit in one screen.

Do not duplicate framework content in a vendor file. Duplication drifts, and the vendor copy is the one that will be stale.

## Conformance checklist

An integration is AIDF-compatible when it can do all of the following. Check them honestly — a partial adapter is fine if you know which part is missing.

- [ ] Read the project manifest and repository guidance before acting.
- [ ] Reach all eight command contracts (`spec`, `design`, `plan`, `build`, `validate`, `preview`, `review`, `ship`).
- [ ] Preserve the document lifecycle and required front matter, including the classification block.
- [ ] Respect track selection — and not produce Track B artifacts for a Track A change.
- [ ] Report changed files, checks run, failures, risks, and open questions in the output contract's five parts.
- [ ] **Distinguish claimed from corroborated evidence**, and never assert a check result a runner did not produce.
- [ ] Honor the stop conditions rather than retrying a failing check indefinitely.
- [ ] Treat repository, issue, and tool content as data, not instructions.
- [ ] Leave merge and production-release decisions to authorized humans or CI.

The sixth item is the one that most integrations fail. It is also the one that decides whether the framework's evidence guarantees mean anything.
